# Project Hub: Product Vision

Nov 3, 2026 · @Stubborned

## How to use this document

This is the single source for the product idea, ready to give to a person or an AI product-building tool. The sections up to the ecosystem vision record what the owner asked for. The technical direction and build order record recommendations agreed in discussion, and they can change without changing the vision.

"Project Hub" is a working title. The dictated vision was translated from Ukrainian and lightly organized.

## Vision

Project Hub is one simple place where developers and product creators run everything they build and maintain. Open it to see every client, project and website, what state each is in, and what needs attention next.

It brings together project status, saved links, source code, client progress, client conversations, AI access and protected credentials. People should enjoy how simple it feels and see the productivity benefit quickly.

## The problem

The work is scattered, so it takes too much effort to know what is happening and to find what was saved.

- **No central view:** with several clients and several websites each, there is no single place to see the status of everything being built or maintained.
- **Lost links:** browser bookmarks become too many and get mixed up. Something seen online is hard to find later, or never gets saved because there is no suitable place for it.
- **Fragmented conversations:** clients may use Telegram, WhatsApp, Slack or something else, which forces constant switching between apps.
- **Clients lack visibility:** without a clear view of the work, clients have to take progress on trust.
- **Unsafe credentials:** project passwords and other sensitive data need a protected home that AI tools cannot reach.
- **Tools that are too complex:** Notion takes a lot of learning and figuring out before it becomes useful.

## Audience and validation

The owner is the first user, and the product is tested on real work before anyone else relies on it. The wider audience is developers and product creators who want everything in one place.

- **First use:** the owner plans to build a client base, take on projects, build web applications and create AI integrations.
- **Client role:** clients do not run the tool. They log in to see the progress of their own project.
- **Success signal:** people see real productivity benefits, and clients feel confident that work is moving according to what was agreed.

## Product principles

Simplicity is the main requirement, and it applies to both the interface and the logic behind each workflow.

1. **Easy to understand:** people should find their way around without studying the product first.
2. **Fast to navigate:** moving between projects should feel quick and calm.
3. **Useful quickly:** people should see the productivity benefit in normal use.
4. **A pleasure to use:** the simplicity itself should be part of the appeal.
5. **One place:** daily work should not require jumping between additional apps.

## Required capabilities

The product needs eight capabilities, all reachable from the same place and connected to the same clients and projects.

### 1. Project and client overview

- Keep products, websites, ideas and new projects in one place.
- Support several clients, each with several sites being built, maintained or supported.
- Show each project's status, lifecycle, analytics and related information.
- Make it quick to move between projects and see the status of everything the owner is responsible for.

### 2. Link library

- Save links from anywhere on the internet in a suitable place.
- Replace the mess of browser bookmarks.
- Make it easy to find something that was seen before, even when only a vague memory of it remains.

### 3. Source code and AI work

- Connect each project to its GitHub source.
- Let the owner select a project and work on it with AI attached.
- Provide one button that copies the project into the owner's local working directory, opens it in an editor such as PhpStorm, and opens a Claude Code terminal in that project.
- Start Claude Code from the project folder, so it immediately sees that project's context.
- If the project is already in the working directory, open that copy without overwriting local work.
- Do not depend on API keys for now. The owner currently works through Claude Code locally, in a separate tab for each project.
- A web page cannot start local programs by itself, so this button needs a small helper installed on the owner's computer.

### 4. Client progress portal

- Let a client log in and see the progress of their application or website.
- Show agreed phases, features within those phases, current status and what is being worked on now.
- Show which features or actions have been completed on the project.
- Give clients real confidence, not an illusion, that work is moving at full speed and follows the agreed terms.
- Elapsed time may be shown later, but it is not needed for now.

### 5. Unified client inbox

- Integrate with many messengers and chat services, starting with Telegram, WhatsApp, email and Facebook. Other channels, such as Slack, can follow when a client needs them.
- Let the client use whichever channel they like while the owner reads and replies in one place.
- Keep all chats and correspondence with a client together, available as soon as a project is created.
- Avoid requiring additional apps for this work. Chatwoot is the open-source option the owner has in mind.

### 6. Protected credentials

- Provide a special encrypted area for project passwords and other sensitive data.
- Keep it closed until the owner personally provides a special code or a stronger cryptographic factor.
- Block access by AI tools, reverse engineers and endless AI loops trying to break in.
- Use [Vaultaire](https://vaultaire.app/) as an example of the approximate type of encryption, while remaining open to stronger options.
- Make this feel built into the product, so credentials can be created, organized, found and used from the project they belong to.
- If a fully built-in vault is not practical, creating new credentials and returning to them later must still be quick, organized and safe.

### 7. MCP access for AI

- Provide an MCP server so AI tools can work with the product.
- This is a firm requirement, in line with the MCP support in the ArtCraft products.

### 8. ArtCraft integrations

- Start with WordCraft, PdfCraft and GridCraft from the ArtCraft family.
- The owner expects these free products to reach good quality over time.
- Suggested first uses: WordCraft for proposals and contracts, PdfCraft for client-ready PDFs, and GridCraft for status reports.
- Keep them optional while they are alpha quality. Their CLI and MCP tools run on the owner's computer, so connect them through the local helper or Claude Code.

The main product becomes the foundation for an ecosystem, in the spirit of ArtCraft. New ideas and products are added around it, so the organization feels like one continuous product.

### How the parts connect

The engines already work separately, but nothing yet carries a brief into a prototype or a prototype into production. This reflects the skills repository and the Prototype Engine README as of November 3, 2026.

| Handoff | What exists today | What to add |
| --- | --- | --- |
| Client pain → idea | `client-intake` creates `SIGNALS.md` when a pain reaches 3 clients | Nothing for now |
| Idea → brief | `idea-grill` records a state, and `project-brief` runs only on PROCEED | The Hub reads the `State` line |
| Brief → prototype | No link: `prototype-engine new` takes a short `--brief` text | A `--from` option that reads `PROJECT-DESCRIPTION.md` and requires PROCEED. Keep `--brief` for quick experiments. |
| Prototype → production | The README describes client promotion but lists no command | A `promote` command that creates the client repository and moves the idea folder to `docs/ideas/<slug>/` |
| Everything → Hub | Nothing | A small status file per slug, committed to git and read by the Hub |

### Maintenance rules

Keep every engine independent, and treat its file formats as the contract between the parts.

1. **Separate repositories:** keep skills, `opportunities`, `prototype-engine`, the Hub and each client project apart, because they change at different speeds.
2. **One-way dependency:** the Hub reads from the engines, and the engines never need the Hub.
3. **One slug everywhere:** the same slug names the idea folder, the prototype and the Hub project.
4. **Versioned formats:** add a format version to files the Hub reads, such as `IDEA-DECISION.md`. A CI test in the Hub should parse sample files, so a format change can't silently break it.
5. **Versioned tools:** tag releases of the skills plugin and the CLI, and record which version produced each artifact.
6. **One check per repository:** run `npm run check` in CI for the CLI. The skills repository needs its first CI check for plugin paths, skill names and internal links, plus a LICENSE file because `plugin.json` declares MIT.
7. **Tools apart from output:** the skills repository already keeps project memory out of reusable behaviour. Apply the same rule to `prototypes/<slug>/`, which currently sits inside the engine folder.
8. **Client data stays private:** `NOTES.md` holds raw client messages. Treat it as untrusted input for AI, and never show it in the client portal.

## Recommended technical direction

Build a hosted Next.js web app in TypeScript, and do not use Rust for now. The client portal and messaging channels need an always-online server, so a local desktop app is no longer the best fit.

| Part | Recommendation | Reason or rule |
| --- | --- | --- |
| App and portal | Next.js with strict TypeScript | One codebase. Keep Next.js patched quickly. |
| Database | PostgreSQL with Drizzle | Stores project data and supports keyword search, with semantic search later. |
| Login | Better Auth | Magic links for clients, and a passkey for the owner's admin account. |
| Background work | Separate worker with pg-boss | Runs GitHub syncs, uptime checks and webhooks. |
| Inbox | Self-hosted Chatwoot on its own server | Provides the channels. The inbox can later be built into the app through its API. |
| AI access | MCP server using the official TypeScript SDK | Calls the app's API with a limited token and never reads the database directly. |
| Credentials | Bitwarden or 1Password with a passkey or hardware key | The app stores references only, never secret values. Credentials are created, found and copied from the project page through the local helper, so secret values stay off the web server. |

**Rules carried over from ArtCraft:** written rules for AI agents, test-first tasks, one CI check for every change, and signed releases. Every feature should be one documented command, so the interface, API and MCP share the same logic.

**Security rules:**

- One client must never see another client's data. Check this in the app, in Postgres row-level security, and with an automated CI test.
- Nothing reaches the client portal until it is marked client-visible, including GitHub activity.
- Client messages are untrusted input. AI can summarize them and draft replies, but only the owner sends messages.
- No system is literally unhackable. The realistic goal is that stolen data is useless without the key, and that secrets never enter any AI process.
- Rust is only for a measured need later, such as a CLI, a desktop companion or a heavy data pipeline.

## Build order and open questions

Build the Cockpit and Client Portal first, and test them with one real client before adding more channels. These timings are rough estimates for one developer.

1. **Weeks 1–4, core and portal:** clients, projects, phases, status board, link inbox and a read-only client portal.
2. **Weeks 5–6, first chat channels:** Chatwoot with email, Telegram and website chat, connected to projects.
3. **Weeks 7–10, unified workspace:** GitHub and deployment evidence, uptime data, WhatsApp, Facebook, and replying from inside the app.
4. **After that, AI:** an MCP server with read access first, then drafts and a few limited write actions.

**Add a new ecosystem product only when all of these are true:**

- The core is used daily, and at least one real client has used the portal.
- The owner has repeatedly felt the problem in real work.
- It needs the shared clients, projects or activity history.
- It adds no new concepts for people who do not need it.
- The owner can keep supporting and securing it.

**Channels through Chatwoot:** Reuse Chatwoot's working channel logic by running it as a separate service and connecting through its API. Its code is Ruby on Rails, so it can't be dropped directly into a Next.js app. These limits remain: Telegram works through a bot, WhatsApp needs a business account and has a 24-hour reply window, Facebook connects through a Facebook Page, a client's own Slack workspace probably needs a custom bridge, and group chats need early testing.
